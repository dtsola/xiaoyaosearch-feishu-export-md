## 1. 总体技术架构

### 架构模式
- **架构类型**：CLI命令行工具（单体应用）
- **部署方式**：npm包发布 + 独立可执行文件分发
- **核心特性**：
  - 跨平台兼容（Windows/macOS/Linux）
  - 模块化设计，易于扩展
  - 支持多租户配置管理
  - 增量导出与断点续传
  - 并发控制与速率限制
- **模块化设计**：配置管理、认证授权、文档导出、知识库导出、资源下载、进度显示、日志管理

## 2. 运行时与编程语言

### 2.1 运行时选型
- **Node.js 18.x+**
  - **选择原因**：
    - 成熟稳定的JavaScript运行时，跨平台兼容性极佳
    - npm生态丰富，大量高质量CLI工具库可供选择
    - 异步I/O模型适合网络密集型应用
    - 内置fetch API（18+），减少依赖
  - **核心优势**：
    - 跨平台支持Windows/macOS/Linux
    - 活跃的社区和长期支持（LTS）
    - 丰富的CLI工具生态
  - **替代方案对比**：
    - **Python**：生态丰富但需要用户安装Python环境，分发成本高
    - **Go**：编译为单一二进制文件，但缺乏飞书官方SDK，HTTP库生态不如Node.js
    - **Rust**：性能极佳但学习曲线陡峭，CLI库生态不如Node.js成熟

### 2.2 编程语言
- **TypeScript 5.x**
  - **选择原因**：
    - 类型安全，减少运行时错误
    - IDE智能提示和重构支持优秀
    - 大型项目可维护性强
    - 编译时错误检查
  - **核心优势**：
    - 接口和类型定义清晰
    - 重构更安全
    - 代码自文档化
  - **替代方案对比**：
    - **JavaScript**：无需编译但缺乏类型检查，大型项目易出错
    - **JSDoc + JavaScript**：有类型提示但不如TypeScript严格和便捷

## 3. CLI框架与工具选型

### 3.1 CLI框架
- **Commander.js 11.x+**
  - **选择原因**：
    - 成熟稳定的CLI框架，GitHub 24k+ stars
    - API简洁优雅，学习曲线平缓
    - 自动生成帮助信息
    - 支持子命令和嵌套命令
    - 支持Git风格的子命令结构
  - **核心优势**：
    - 声明式命令定义
    - 自动生成--help和--version
    - 支持选项别名和默认值
    - 支持可变参数
  - **替代方案对比**：
    - **Yargs**：功能更强大但API更复杂，对于本项目Commander已足够
    - **Oclif**：功能完善但过于重量级，适合大型多命令CLI工具
    - **CAC**：轻量但生态不如Commander成熟

### 3.2 交互式配置
- **Inquirer 9.x+**
  - **选择原因**：
    - 优雅的交互式命令行界面
    - 支持多种输入类型（输入、确认、列表、密码等）
    - 支持异步验证
    - 美观的界面样式
  - **核心优势**：
    - 用户体验好
    - 内置输入验证
    - 支持分页和筛选
  - **使用场景**：
    - `feishu-export init` 配置初始化
    - 敏感信息输入（App Secret）

### 3.3 进度显示
- **cli-progress 3.x+**
  - **选择原因**：
    - 支持多种进度条样式
    - 支持多进度条同时显示
    - 跨平台兼容性好
    - 支持预设样式
  - **核心优势**：
    - 实时显示进度百分比
    - 显示ETA（预计剩余时间）
    - 支持自定义格式
  - **使用场景**：
    - 批量文档导出进度
    - 知识库导出进度
    - 图片下载进度

## 4. 网络通信与API

### 4.1 HTTP客户端
- **Axios 1.x+**
  - **选择原因**：
    - 支持请求/响应拦截器，便于处理Token
    - 自动JSON转换
    - 请求取消支持
    - 超时配置
    - 广泛使用，社区活跃
  - **核心优势**：
    - 拦截器机制适合处理认证Token刷新
    - 统一的错误处理
    - 支持请求和响应转换
  - **替代方案对比**：
    - **Fetch API**：内置但缺乏拦截器，需要手动处理Token
    - **Got**：功能强大但API不如Axios直观
    - **ky**：轻量但功能相对简单

### 4.2 速率限制
- **Bottleneck 2.x+**
  - **选择原因**：
    - 成熟的令牌桶算法实现
    - 支持并发控制和限流
    - 支持优先级队列
    - 自动重试和指数退避
  - **核心优势**：
    - 避免触发API限流
    - 可配置并发数和请求间隔
    - 支持动态调整限流参数
  - **使用场景**：
    - 飞书文档API调用限制（5次/秒）
    - 媒体下载API限制（10次/秒）
    - Token刷新限制（100次/分钟）

### 4.3 重试机制
- **Axios-retry (或自研基于Bottleneck)**
  - **选择原因**：
    - 网络错误自动重试
    - 指数退避策略
    - 可配置重试次数和条件
  - **核心优势**：
    - 提高导出成功率
    - 减少用户手动重试

## 5. 文件与配置管理

### 5.1 配置管理
- **cosmiconfig 8.x+**
  - **选择原因**：
    - 支持多种配置文件格式（JSON、YAML、JS、TS）
    - 约定优于配置，自动搜索配置文件
    - 支持配置文件缓存
    - 广泛使用于开源项目
  - **核心优势**：
    - 灵活的配置文件位置
    - 支持多配置文件加载
    - 配置文件热重载支持
  - **使用场景**：
    - 加载 `~/.feishu-export/config.json`
    - 支持项目级配置文件 `.feishu-exportrc`

### 5.2 文件操作
- **fs-extra 11.x+**
  - **选择原因**：
    - Node.js fs模块的增强版
    - Promise API支持
    - 自动创建父目录
    - 更友好的API设计
  - **核心优势**：
    - `outputFileSync` 自动创建目录
    - `remove` 递归删除
    - `copy` 递归复制
    - `readJson` / `writeJson` JSON读写
  - **替代方案对比**：
    - **Node.js fs**：原生但缺乏Promise API和便利方法
    - **fs-jetpack**：API更友好但生态不如fs-extra

### 5.3 路径处理
- **Node.js path (内置)**
  - **选择原因**：
    - 内置模块，无需额外依赖
    - 跨平台路径兼容
    - 处理路径拼接、解析、规范化

## 8. 开发工具选型

### 8.1 包管理
- **pnpm 8.x+**
  - **选择原因**：
    - 节省磁盘空间（硬链接机制）
    - 安装速度快
    - 严格的依赖管理
    - 支持Monorepo
  - **核心优势**：
    - 节省50%以上磁盘空间
    - 依赖安装速度快2-3倍
    - 避免幽灵依赖问题
  - **替代方案对比**：
    - **npm**：内置但速度慢，占用空间大
    - **Yarn**：功能完善但Pnpm性能更优

### 8.2 构建工具
- **tsup 8.x+**
  - **选择原因**：
    - 基于esbuild，构建速度快
    - 专为TypeScript库设计
    - 支持多种输出格式（CJS、ESM、IIFE）
    - 支持代码拆分
    - 零配置即可使用
  - **核心优势**：
    - 构建速度快10-100倍
    - 自动生成类型声明
    - 支持双包发布（CJS + ESM）
  - **替代方案对比**：
    - **webpack**：功能强大但配置复杂，构建速度慢
    - **rollup**：适合库打包但配置较繁琐
    - **esbuild**：速度快但tsup封装得更好

### 8.3 二进制打包
- **pkg 8.x+ (备选：nexe 4.x+)**
  - **选择原因**：
    - 将Node.js项目打包为独立可执行文件
    - 无需用户安装Node.js
    - 支持多平台（Windows/macOS/Linux）
  - **核心优势**：
    - 用户体验好（单文件分发）
    - 减少依赖安装问题
  - **替代方案对比**：
    - **nexe**：打包后文件更大，但配置更简单
    - **Nexe**：编译速度更快，但兼容性不如pkg

### 8.4 代码规范
- **ESLint 8.x+ + Prettier 3.x+**
  - **选择原因**：
    - ESLint：代码质量检查
    - Prettier：代码格式化
    - 两者配合使用效果最佳
  - **配置**：
    - TypeScript规则集
    - Node.js环境
    - Prettier集成

### 8.5 类型检查
- **TypeScript Compiler (tsc)**
  - **选择原因**：
    - 编译时类型检查
    - 严格模式捕获潜在错误
  - **tsconfig.json配置**：
    - `strict: true`
    - `esModuleInterop: true`
    - `skipLibCheck: true`

### 8.6 测试框架
- **Vitest 1.x+**
  - **选择原因**：
    - 快速（基于Vite）
    - 兼容Jest API
    - 原生ESM支持
    - TypeScript支持良好
  - **核心优势**：
    - 执行速度快
    - 开发体验好
    - 内置代码覆盖率
  - **替代方案对比**：
    - **Jest**：功能完善但速度较慢
    - **Mocha + Chai**：灵活但配置繁琐

## 10. 技术选型对比总结

### 10.1 运行时对比

| 运行时 | 优势 | 劣势 | 适用场景 |
|------|------|------|---------|
| **Node.js** ✅ | 跨平台、生态丰富、异步I/O | 单线程、CPU密集性能弱 | 网络密集型CLI工具 |
| Python | 生态丰富、语法简洁 | 分发成本高、需安装环境 | 数据处理、机器学习 |
| Go | 编译为单一文件、性能高 | 缺乏飞书SDK、生态不如JS | 系统工具、后端服务 |
| Rust | 性能极佳、内存安全 | 学习曲线陡、CLI生态不成熟 | 对性能要求极高的工具 |

### 10.2 CLI框架对比

| 框架 | 优势 | 劣势 | 适用场景 |
|------|------|------|---------|
| **Commander.js** ✅ | API简洁、成熟稳定、生态好 | 功能相对基础 | 中小型CLI工具 |
| Yargs | 功能强大、参数解析完善 | API复杂、学习曲线陡 | 大型复杂CLI工具 |
| Oclif | 功能完善、插件系统 | 过于重量级 | 企业级多命令CLI |
| CAC | 轻量、API简洁 | 生态不如Commander | 小型简单CLI工具 |

### 10.3 HTTP客户端对比

| 客户端 | 优势 | 劣势 | 适用场景 |
|------|------|------|---------|
| **Axios** ✅ | 拦截器、API简洁、社区活跃 | 包体积略大 | 需要请求/响应拦截的场景 |
| Fetch API | 内置、无依赖 | 缺乏拦截器、功能简单 | 简单HTTP请求 |

|------|------|------|---------|
| **pnpm** ✅ | 快速、节省空间、严格依赖 | 相对较新 | 大型项目、Monorepo |
| npm | 内置、兼容性好 | 速度慢、占用空间大 | 小型项目 |
| Yarn | 功能完善、性能好 | 占用空间比pnpm大 | 中大型项目 |

## 12. 技术选型总结

### 核心原则
1. **成熟稳定优先**：选择社区成熟、文档完善的技术栈
2. **跨平台兼容**：确保Windows/macOS/Linux全平台支持
3. **用户体验优先**：选择能提升用户体验的工具（进度条、交互式配置）
4. **类型安全**：TypeScript确保代码质量
5. **开发效率**：选择开发体验好的工具（tsup、Vitest）

### 技术亮点
✅ **TypeScript全覆盖**：编译时类型检查，减少运行时错误
✅ **零配置分发**：支持npm安装和独立二进制文件两种分发方式
✅ **优雅的交互体验**：inquirer + cli-progress提升用户体验
✅ **高效的并发控制**：bottleneck实现速率限制，避免API限流
✅ **增量导出**：元数据记录实现增量导出，节省时间和API调用
✅ **断点续传**：支持中断后继续导出

### 升级路径

| 阶段 | 用户量 | 导出量 | 升级方案 |
|------|--------|---------|---------|
| **初期** | < 100 | < 1000文档/天 | 单机运行，当前架构 |
| **成长期** | 100-1000 | < 10000文档/天 | 优化并发控制，增加缓存 |
| **扩展期** | > 1000 | > 10000文档/天 | 考虑云端服务，分布式导出 |
